== はじめに：プロンプトエンジニアリングの終焉と「ループ」の時代

[quote, Boris Cherny (Claude Code Lead)]
____
「私はもう、AI に直接プロンプトを打って細かく指示を出していません。
私が作っているのは **『ループ（仕組み）』** であり、そのループが AI に指示を出して自律的に動かしています。」
____

2026年半ば、Claude Code の開発を率いる Boris Cherny 氏のこの発言をきっかけに、AI 開発者の間で爆発的な注目を集めている新しいパラダイムが **「ループエンジニアリング（Loop Engineering）」** です。

これまでの AI 活用は、「いかに巧みなプロンプトを書くか（プロンプトエンジニアリング）」という 1 問 1 答のテクニックが中心でした。しかし、Google Antigravity CLI（`agy`）をはじめとする自律型 AI エージェントの登場により、開発者の役割は根本から変化しました。

[TIP]
.ルンバの例えで理解するループエンジニアリング
====
人間が自ら掃除機をかける（1 つずつプロンプトを打つ）のではなく、**ルンバ（AI エージェント）が部屋中をスムーズに掃除できるように、床の障害物を片付け、充電ドックを配置し、進入禁止エリア（ルールとガードレール）を設定する** こと。これこそがループエンジニアリングの本質です。

[cols="1,1,2", options="header"]
|===
| ルンバの環境づくり（掃除の自動化） | ループエンジニアリング（AI開発の自動化） | 役割・効果
| **ルンバ（お掃除ロボット）** | **AI エージェント (`agy`)** | 自律的に動いてタスクを完遂する主体
| **部屋のドアを閉める（囲い）** | **サンドボックス (Dev Containers)** | ホストを汚さず、壊れても安全な隔離空間
| **床の障害物・コードの片付け** | **環境ノイズの排除・依存関係固定** | エージェントが迷走・スタックする原因の事前除去
| **充電ドック（自律帰還・給電）** | **高速なテスト・観測コマンド** | `hugo` や `npm test` による即時エラー検知・自己修復
| **進入禁止エリア（バーチャル壁）** | **ガードレール (`settings.json` / Rules)** | `allowNonWorkspaceAccess: false` や破壊操作の抑止
| **部屋の間取りマップの自動学習** | **メタ進化ループ (`Learnings.md`)** | 過去のセッションから学び、次回より最適に走行
| **人間の仕事（掃除機を手放す）** | **ループ設計者（プロンプト打ちをやめる）** | 人間は「環境と検証基準を整えてスイッチを押すだけ」
|===
====

本記事では、ループエンジニアリングの基礎概念から、セッションログを活用した「AI 自己進化ループ」、そして Antigravity CLI（`agy`）での具体的な実践テクニックまでを徹底解説します。

'''

== エージェントを取り巻く「3 つのループ構造」

ループエンジニアリングでは、AI の動作を 3 つの階層的なフィードバックループとして設計します。

[cols="1,2,2", options="header"]
|===
| ループ層 | 主体とフィードバック源 | 最適化の目的
| **1. インナーループ (Inner Loop)** | AI エージェント ⇄ ツール（ファイル操作・シェル・Linter） | **自律実行と自己修復力の最大化**（人間の介入なしにエラーを解消して完遂）
| **2. メタ進化ループ (Meta Learning Loop)** | セッションログ ⇄ `AGENTS.md` / `Learnings.md` | **経験の蓄積と自己進化**（同じ失敗を二度と繰り返さない仕組み化）
| **3. アウターループ (Outer Loop)** | 人間 / CI ⇄ AI エージェント | **方向性の制御と品質保証**（ゴール定義・アーキテクチャレビュー・安全性）
|===

=== 1. インナーループ（実行と自己修復）

インナーループは、エージェントが目標に向かって自律的に繰り返す最小単位のサイクルです。

[source,text]
----
[1. Plan (思考・計画)]
  │
  ▼
[2. Action (ツール実行)]
  │  (view_file / replace_file_content / run_command)
  │
  ▼
[3. Observe (実行結果の観測)]
  │  (Exit Code / Stdout / Stderr / Linter)
  │
  ├──► [成功 / 完了] ──► 終了（ゴール達成）
  │
  └──► [エラー / 失敗]
         │
         ▼
       [4. Reflect & Fix (自己修復・分析)]
         │
         └────────► [1. Plan] へ戻り再試行
----

エージェントが「エラーが出たのでどうしますか？」と人間に聞くことなく、**ログを自己分析してコードを直し、再検証して前に進めるか** がこのループの肝です。

=== 2. メタ進化ループ（自己学習とルールの自動更新）

これまでの AI ツールは、セッションを閉じると過去の試行錯誤や反省がリセットされていました。
メタ進化ループは、**セッション中のエラーやユーザーからの指摘をナレッジ・ルールとして永続化し、次回のセッションの精度を自動で向上させるサイクル** です。

[source,text]
----
[セッションの実行]
  │  (試行錯誤・エラー解決・ユーザーからのフィードバック)
  │
  ▼
[知見の抽出 (Reflect)]
  │  "次回から同じミスを防ぐための汎用ルールは何か？"
  │
  ├──► AGENTS.md へ 1 行追記（行動ポリシーの自己進化）
  │
  └──► Learnings.md へ知見蓄積（プロジェクト知識の永続化）
----

'''

== 5 分で実践！ループエンジニアリング 3 つのステップ

Boris Cherny 氏らが提唱するループエンジニアリングは、今すぐ 5 分で実践できます。

=== Step 1: 1 行プロンプトでルールファイルを自己進化させる

タスクが完了した際や、エージェントの挙動を修正したセッションの終わりに、以下の **1 行プロンプト** をエージェントに入力します。

[source,text]
----
"今回のセッションでの反省点や重要な仕様を、AGENTS.md に 1 行で追記してルールを更新してください"
----

Antigravity CLI では、`/learn` スラッシュコマンドを使っても同様にセッションの学びをルールに永続化できます。

これにより、人間がコーディング規約を手動でメンテしなくても、**「失敗するたびに勝手に賢くなる開発環境」** が育ちます。

=== さらに先へ：1 行プロンプトすら不要にする「完全自律型自己進化ループ」

「セッション終了時に 1 行プロンプトを打つことすら自動化したい」という場合、**`AGENTS.md` の自律動作ポリシー自体に自己進化ルールをあらかじめ組み込んでおく** のが最も強力なアプローチです。

[source,markdown]
.AGENTS.md への自己進化ポリシーの組み込み
----
# 自律動作ポリシー
- 軽微な選択肢や標準的な実装判断は、ユーザーに都度質問せず、ベストプラクティスに従って自動で進めてください。
- コマンド実行やテストでエラーが発生した場合も、まずはログを自己分析して自動修正を試みてください。
- 破壊的な変更以外は、質問や確認を挟まずに完了まで自律的に実行してください。
- **自己進化・自動記録**: 新しいトラブルの解決や環境固有の重要な仕様を発見した場合は、ユーザーからの指示を待たずに自発的に `Learnings.md`（および必要に応じて本 `AGENTS.md`）へ追記・更新してタスクを完了してください。
----

こうしておけば、ユーザーは普段通りタスクの指示を出すだけで、**エージェントが「これは新しい知見・教訓だ」と判断したときに、自発的にナレッジを記録してタスクを完了** します。ユーザーの入力コストは完全にゼロになります。

=== Step 2: `Learnings.md` による知見の永続化

特定のフレームワーク固有のハマりどころや環境設定の癖は、プロジェクトルートの `Learnings.md`（または `.agents/knowledge/`）に自動蓄積させます。

[source,markdown]
.Learnings.md の例
----
# Learnings & Solutions

## Hugo + AsciiDoc
- AsciiDoc のネストリストはスペースインデントではなく `**`（アスタリスク2個）で書く必要がある。
- Hugo の並行ビルド時に Docker コンテナを呼び出す場合、入出力パイプの競合を防ぐため `flock` による排他制御が必要。
- 記事の日付（date）が現在時刻より未来の場合、Hugo は future post としてスキップするため注意。
----

新しいセッションを開始するたびにエージェントがこのファイルを自動参照することで、過去の失敗を即座に回避できます。

=== Step 3: ルール・ナレッジの定期メンテナンス

ルールが増えすぎると、コンテキストウィンドウを圧迫し、ルールの衝突が発生します。定期的に以下のプロンプトを実行してクリーンアップします。

[source,text]
----
"AGENTS.md と Learnings.md を見直し、重複しているルールの統合と陳腐化した項目の削除を行ってください"
----

'''

== なぜ「サンドボックス（Dev Containers）」なしではループが破綻するのか？

ループエンジニアリングを語る上で、避けて通れない根本的な問いがあります。

[quote]
____
「サンドボックスやコンテナを使わずに、普段のローカル環境（ホストOS）でエージェントを自律走行させれば良いのでは？」
____

結論から言うと、**サンドボックス（隔離環境）なしのループエンジニアリングは、ほぼ確実に破綻します。** 人間の介入（Human in the Loop）が爆発し、ループを回す意味そのものが失われてしまうためです。理由は大きく 2 つあります。

=== 1. 「安全性」と「確認プロンプト」のジレンマ

ホスト OS 上で AI エージェントにターミナル操作やファイル編集を自由に許可すると、以下の重大なリスクが常に付きまといます：

* 誤った `rm` や破壊的なスクリプトによる個人ファイル・別プロジェクトの損失
* 不用意なパッケージインストールによるホスト環境の汚染や依存関係の破壊
* 意図しない外部ネットワークへの通信

このリスクを防ぐため、開発者はツール実行ごとに **「実行して良いですか？ (y/n)」という確認プロンプト（Tool Confirmation）を挟まざるを得なくなります**。

[source,text]
----
[ホストOSでの実行: 確認地獄]
  エージェント思考 ──► コマンド提案 ──► 【人間の承認待ち (y/n)】 ──► 実行
         ▲                                                            │
         │                                                            ▼
         └─────────── 【人間の承認待ち (y/n)】 ◄── 自己修復コード生成 ◄─┘
----

エージェントがエラーを自己修復して 1 つのタスクを終えるまでに、人間が 5 回も 10 回も「y」を押し続けるのであれば、それは **「自律ループ」ではなく「ただの面倒な手動ペアプロ」** に成り下がってしまいます。

==== コンテナ（Dev Containers）がもたらすブレイクスルー
コンテナ環境の最大の特徴は、**「どれだけ破壊されても、1 秒で元のクリーンな状態に再構築（Rebuild）できるディスポーザブル（使い捨て）性」** にあります。

* 最悪のケースでもホスト OS に一切の被害が及ばない
* だからこそ、人間は安心して `permissions.allow` を開放し、**「確認プロンプトなしの完全手放し（Human-out-of-the-loop）」で 50 回でも 100 回でも自律ループを回させることができる**

「ルンバの例え」で言えば、**「部屋のドアを閉めて危険な階段から落ちないように囲いを作る（サンドボックス化）からこそ、人間がルンバの後ろをついて歩く（Human in the loop）必要がなくなる」** ということです。

=== 2. 「環境ノイズ」による迷走ループの撲滅

ホスト OS には、過去にインストールした別バージョンの言語ランタイム、グローバル環境変数、ローカル独自のパス設定など、無数の「不確実な状態（環境ノイズ）」が存在します。

ホスト環境でテストが失敗した際、エージェントは **「コードのバグ」なのか「OS の環境設定の不整合」なのかを区別できません**。その結果、本来触る必要のないシステム設定やグローバルパッケージを弄り始め、トークンとコンテキストを浪費して無限ループ（迷走）に陥ります。

Dev Containers を使えば、依存関係がコード（Dockerfile / devcontainer.json）として厳密に固定されたクリーンな土俵が手に入ります。エージェントは環境トラブルに足を取られることなく、**「純粋なコードとテストのフィードバックループ」だけに 100% 集中** できます。

'''

== Antigravity CLI でループを滑らかに回す 5 つの設計テクニック

Antigravity CLI（`agy`）環境において、エージェントの自律ループを極限まで加速・安定させるための具体的な設計テクニックです。

=== 1. 自律動作ポリシー（`AGENTS.md`）の標準配備

プロジェクトのルートにある `AGENTS.md` に **「自律ループを止まらせない行動指針」** と **「プロジェクト固有ルール」** を定義しておきます。

[source,markdown]
.AGENTS.md の最新構成例
----
# 自律動作ポリシー
- 軽微な選択肢や標準的な実装判断は、ユーザーに都度質問せず、ベストプラクティスに従って自動で進めてください。
- コマンド実行やテストでエラーが発生した場合も、まずはログを自己分析して自動修正を試みてください。
- 破壊的な変更(未コミットの変更を破棄するなど)以外は、質問や確認を挟まずに完了まで自律的に実行してください。
- **自己進化・自動記録**: 新しいトラブルの解決や環境固有の重要な仕様・ノウハウを発見した場合は、ユーザーからの明示的な指示を待たずに、自発的に `Learnings.md`（および必要に応じて本 `AGENTS.md`）へ追記・更新してタスクを完了してください。

# プロジェクト固有ルール
- **環境保全**: メイン環境の OS にパッケージ（Ruby や Asciidoctor 等）を直接追加インストールせず、専用 Docker コンテナ連携アーキテクチャを維持してください。
- **AsciiDoc 執筆**: 入れ子リストは必ず `**`（アスタリスク2個）で記述し、アスキーアートは全角ズレを防ぐオープンツリー形式（`├──►` 等）を採用してください。
- **Hugo 検証**: 記事の日付（`date`）は現在時刻以前を指定し、作成・修正後は必ず `hugo --cleanDestinationDir` でビルドを検証してください。
- **知見の参照・蓄積**: 過去のトラブルシューティングや詳細は `Learnings.md` を参照・更新してください。
----

=== 2. 高速かつ明瞭な観測環境（Fast Observability）

エージェントの自己修復ループを高速化するためには、検証環境の最適化が必須です。

* **短周期で実行できるテスト・ビルドコマンドの提供**
** 実行に数分かかる重いテストスイートは、エージェントのループを著しく鈍化させます。
** `npm test -- --bail` や `hugo --panicOnWarning` など、失敗が即座にわかり、最小限で検証できるコマンドを用意します。
* **明確な終了ステータス（Exit Code）**
** エラー時に exit code `0` で正常終了してしまうスクリプトは、エージェントに「成功した」と誤認させます。失敗時は必ず非ゼロを返す設計にします。
* **Dev Containers によるクリーンなサンドボックス**
** 依存関係がすべて整ったコンテナ環境を用意することで、環境起因のノイズエラーを排除し、コード本来のフィードバックに集中させます。

=== 3. 摩擦のないパーミッション設計（Frictionless Permissions）

コマンドを実行するたびに確認ダイアログ（Tool Confirmation）が出ると、自律実行が停止します。
`~/.gemini/antigravity-cli/settings.json` の `permissions.allow` を設定し、安全な日常操作を全自動化します。

[source,json]
----
{
  "permissions": {
    "allow": [
      "command(hugo*)",
      "command(git status)",
      "command(git diff)",
      "command(git log)",
      "command(git add)",
      "command(git commit)",
      "command(npm test)",
      "command(cat)",
      "command(grep)",
      "command(ls)",
      "command(mkdir)"
    ]
  }
}
----

=== 4. サブエージェント（Subagents）によるループの分離と並行化

1 つの会話スレッドで長大なループを回し続けると、**トークン消費の爆発** と **Context Drift（文脈の見失い）** が発生します。これを防ぐのがサブエージェントです。

[source,text]
----
[Parent Agent (親エージェント: オーケストレーター)]
  │  • 全体の進行管理・マイルストーン分割
  │  • 最終的な品質判定・コードマージ・ユーザー報告
  │
  ├──► [Subagent A: Research (調査特化)]
  │      • 複数ライブラリ・API仕様の並行調査（Flashモデル）
  │      • 調査結果の要約（サマリー）のみを親へ返却
  │
  ├──► [Subagent B: Branch Refactor (隔離実装)]
  │      • 分岐ブランチ（Workspace: "branch"）で大胆なコード改修
  │      • テスト通過まで内部で自己修復ループを完結
  │
  └──► [Subagent C: Security & Review (レビュー特化)]
         • 変更差分の脆弱性・規約違反チェック
         • 合格/不合格の判定と改善提案を親へ返却
----

==== サブエージェントの起動方法
ユーザーからチャットで「サブエージェントを使って並行調査して」と指示するだけで、親エージェントが内部的に `invoke_subagent` ツールを呼び出してバックグラウンドで並行稼働させます。

=== 5. スキル（Skills）による標準パスの固定化

定型タスクは `SKILL.md` として手順を明文化し、試行錯誤のターン数を最小化します。

'''

== 実践例：ブログ執筆における自己修復＆自己進化ループ

当ブログ環境（Hugo + AsciiDoc + Antigravity CLI）におけるループエンジニアリングの実例です。

[source,text]
----
1. [User] "ループエンジニアリングについて新しい記事を書いて"
   │
   ├──► 2. [Inner Loop: Action] `new-post` で雛形作成 ＆ 本文執筆
   │
   ├──► 3. [Inner Loop: Observe] `hugo --cleanDestinationDir` を実行
   │      [Error 検知] "HTML が生成されない（future post によるスキップ）"
   │
   ├──► 4. [Inner Loop: Fix] 日付メタデータを現在時刻に自動修正して再ビルド ──► 成功！
   │
   ├──► 5. [User Feedback] "AsciiDoc のネストリストがフラットになっていたよ"
   │      [Action] 本文のリスト記法を `**`（AsciiDoc仕様）に自己修正
   │
   ├──► 6. [Inner Loop: Observe] 並行ビルド時に本文が空になる現象を検知
   │      [Root Cause] Hugo の並行実行による `docker run` の I/O パイプ切断
   │      [Fix] `~/.local/bin/asciidoctor` に `flock` による排他制御を導入して解決！
   │
   └──► 7. [Meta Learning Loop: Zero-Prompt Evolution]
          - ユーザーがプロンプトを打たなくても、得られた知見を `Learnings.md` に自動蓄積
          - `AGENTS.md` に「環境保全」「AsciiDoc記法」「自己進化ポリシー」を自動定着
----

エージェントは単にコードを書くだけでなく、**「実行 → エラー観測 → 自己修復 → フィードバック反映 → 根本原因特定・解決 → ルールとナレッジへの完全自動定着」** という多重の自律ループを滑らかに完走しています。
