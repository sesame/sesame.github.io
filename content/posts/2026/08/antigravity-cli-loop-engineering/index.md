## ループエンジニアリングとは

Google の Addy Osmani 氏は、エッセイ [『Loop Engineering』(2026-06-07)](https://addyosmani.com/blog/loop-engineering/) の中で、ループエンジニアリングを
次のように定義しています。

> エージェントに指示を与える役割を自分自身から切り離し、代わりにその指示を行うシステムを設計すること
> - [Loop Engineering(2026-06-07)](https://addyosmani.com/blog/loop-engineering/)

Claude Code の開発を率いるボリス・チェルニー（Boris Cherny）氏も、次のように語っています。

> 「私はもう、Claude に直接指示を与えていません。Claude に指示を与え、何をすべきかを判断させるループを実行しています。私の仕事は **『ループ（仕組み）』** を書くことです。」
> — Boris Cherny (Head of Claude Code, Anthropic)

従来のプロンプトエンジニアリングは、「人間が AI と対話しながら 1 問 1 答で出力を調整する」作業でした。
しかし、AI が進化して自分でコマンドを叩き、ファイルを読み書きできるようになった現在の自律型エージェントの時代においては、
人間が間に入って手動でプロンプトを仲介していては、作業が止まり人間も疲弊してしまいます。

これは、人間がプロンプトを打つ作業自体が、最大のボトルネックとなっていることを意味します。

AIコーディングエージェントを最大限に活用するためには、人間によるボトルネックを極限まで減らすことが重要であり、
そのためにシステム側に自律的に動作し改善を行うループを用意する必要があるということを述べています。

## 自律ループを支える基本要素

Addy Osmani 氏は自律ループを成立させるための **5つの基本要素（Primitives）** と **1つの外部メモリ（Memory）** を整理しています。

| 構成要素 | ループ内での役割 | 具体的な実装例 |
| :--- | :--- | :--- |
| **1. Automations（自動化）** | 定期実行・タスクの探索とトリガー | 定期監視（`/schedule`）、ゴール駆動実行（`/plan`） |
| **2. Worktrees（並行隔離）** | エージェント作業の衝突を防ぐ環境分離 | `git worktree`、独立ブランチでの作業 |
| **3. Skills（スキル）** | 特定タスクに必要な手順書・知識のオンデマンド提供 | Agent Skills（`SKILL.md` / Runbook） |
| **4. Plugins / Connectors** | 外部ツールや API との接続 | MCP（GitHub MCP、各種外部ツール連携） |
| **5. Sub-agents（サブエージェント）** | 実装担当（Maker）と検査担当（Checker）の分離 | 調査用・レビュー用のサブエージェント分割 |
| **+ Memory（外部記憶）** | セッションを跨いだ知見・進捗の永続化 | **`Learnings.md`** や `AGENTS.md` |

特に重要なのが **「Memory（外部記憶）」** です。

Addy 氏が *「The agent forgets, the repo doesn't（エージェントは忘れるが、リポジトリは忘れない）」* と述べている通り、
LLM のコンテキストウィンドウの外側（リポジトリ内の Markdown 等）に状態やルールを逃がして引き継ぐことで、初めてセッションが途切れても継続する自律ループが完成します。

AIコーディングエージェント自体の機能および周囲の環境を用意し、自律ループを支える基本要素を整え自律ループを回すことで
ループエンジニアリングを目指します。

## ループエンジニアリングを成立させる 3 つの核心要件

製品やツールの垣根を越えて、自律ループを破綻させずに回し続けるためには、**「自走（Run）」「自己修復（Correct）」「自己進化（Evolve）」** を支える 3 つの核心要件（足場）が不可欠です。

```text
 ┌─────────────────────────────────────────────────────────────┐
 │                ループエンジニアリングの 3 本柱              │
 ├──────────────────────────────┬──────────────────────────────┤
 │ ① ノンブロッキングな実行権限 │ ▶ 【自走の条件】             │
 │    （承認待ちの排除）        │    人間の確認待ちで止まらない │
 ├──────────────────────────────┼──────────────────────────────┤
 │ ② 高速な検証環境            │ ▶ 【自己修復の条件】         │
 │    （Fast Observability）    │    失敗を即座に検知して直す   │
 ├──────────────────────────────┼──────────────────────────────┤
 │ ③ 2 層構造の外部記憶         │ ▶ 【自己進化の条件】         │
 │    （基本方針とナレッジの分離│    コンテキストを圧迫せず知見 │
 │     による自己進化）         │    を次回セッションへ引き継ぐ │
 └──────────────────────────────┴──────────────────────────────┘
```

### 1. ノンブロッキングな実行権限（自走の条件）
エージェントがコマンドを実行するたびに対話型の承認プロンプト（Confirmation）を挟むと、自律ループがブロックされて人間が再びボトルネックになります。
日常的に使用するテスト・ビルド・Git コマンドを事前登録し、**「確認待ちによるループ停止」を排除**することが自走の第一歩です。

### 2. 高速な検証環境（自己修復の条件）
エージェントが「自分の変更が正しかったか」を即座に判定できるよう、検証コマンド（Fast Observability）を整備します。

- **数秒で完了する**: 検証に時間がかかると自己修復ループが鈍化します。
- **明確な終了コード（Exit Code）**: 成功時は `0`、失敗時は非ゼロを返し、成否を機械判定できるようにします。
- **わかりやすいエラー出力**: 失敗箇所の行番号やスタックトレースを標準エラー出力（stderr）に出力します。

### 3. 2 層構造の外部記憶（自己進化の条件）

エージェントのコンテキスト肥大化を防ぎつつ、過去の失敗やプロジェクト固有ノウハウを引き継ぐため、外部記憶を **「常時ロード層」** と **「オンデマンド参照・自己進化層」** の 2 つに分離します。

```text
 ┌─────────────────────────────────────────────────────────────┐
 │ 【第 1 層：常時ロード層】 AGENTS.md （20〜50行程度）       │
 │  ・全セッションの毎ターンで必ず自動注入される最重要ポリシー   │
 │  ・自律完遂の方針、破壊的変更の確認、コミット規約            │
 │  ・「知見は Learnings.md を参照・更新せよ」という指示         │
 └──────────────────────────────┬──────────────────────────────┘
                                │ 必要時に参照 / 完了時に追記
                                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ 【第 2 層：オンデマンド参照・自己進化層】 Learnings.md      │
 │  ・過去のトラブルシューティング、環境固有の仕様、回避策     │
 │  ・毎ターン全行を読み込むのではなく、ツールで必要な知見を参照│
 │  ・タスク完了時（または /learn）にエージェントが自動更新     │
 └─────────────────────────────────────────────────────────────┘
```

#### なぜ 1 つの指示ファイルにまとめてはいけないのか？
初期のエージェント活用では、セッションが切れた際のコンテキスト消失を防ぐため、`AGENTS.md` や `CLAUDE.md` に過去のエラー対策や注意点をすべて書き足す手法が取られていました。しかし、この単一ファイルへの肥大化には 2 つの技術的欠陥があることが学術研究および実務ベンチマークで明らかになっています。

1. **トークン消費とコストの爆発（Context Bloat）**:
   数十〜数百項目におよぶ知見が毎ターン送信され、何もしなくても会話開始時点で大量の入力トークンを消費し、レイテンシと API コストが急増します。
2. **指示の希釈と見落とし（Attention Dilution / "Lost in the Middle" 現象）**:
   スタンフォード大や UC バークレーの研究 **[『Lost in the Middle: How Language Models Use Long Contexts』(Liu et al., 2023)](https://arxiv.org/abs/2307.03172)** で示された通り、LLM はプロンプトが長大化・ノイズ化するほど内部の重要な指示に対するアテンション（注意）が希釈され、指示遵守率（Instruction-following accuracy）が低下します。結果として「破壊的変更は必ず確認する」といった最重要ルールが見落とされるリスクが高まります。


#### 2 層分離設計の動作メカニズム

この課題を解決するのが、**`AGENTS.md`（常時ロード層）** と **`Learnings.md`（オンデマンド参照・自己進化層）** の 2 層構造です。

##### なぜ `Learnings.md` は「オンデマンド」になるのか？
根本的な理由は、**エージェントツールのシステム仕様** にあります。

- **`AGENTS.md`（システムによる常時強制ロード）**:
  Antigravity のシステム仕様として、毎ターンの API リクエスト時にプロンプトのコンテキストへ無条件で自動注入されます。
- **`Learnings.md`（通常ファイルとしてのオンデマンド参照）**:
  リポジトリ内の通常のソースコードと同様、システムが毎ターン勝手に全行をプロンプトに流し込むことはありません。エージェントがファイル操作ツール（`view_file` や `grep_search`）を使って**必要な時だけ能動的に読みに行く通常ファイル**として扱われます。

##### 「ポインタ（参照）」としての `AGENTS.md`
単に `Learnings.md` をリポジトリに置いただけでは、エージェントはそのファイルの存在に気づかない可能性があります。そこで、常時ロードされる `AGENTS.md` に以下のような **ポインタ（索引指示）** を 1 行だけ記述します。

```markdown
- **知見の参照**: 詳細な技術仕様や過去のトラブルシューティングは Learnings.md を参照する。
```

これにより、プログラミングにおける「ポインタ・参照渡し」と同じ構造が作られます。

1. **エージェント起動時**:
   コンテキストには軽量な `AGENTS.md`（数十行）のみが注入され、トークン消費を最小限に抑えます。エージェントは「困ったときは `Learnings.md` という外部ナレッジがある」というポインタ情報のみを把握しています。
2. **タスク実行時（オンデマンド参照）**:
   ビルドエラーや環境固有の仕様に直面した際、エージェントは `AGENTS.md` のポインタ指示に従い、ツール経由で `Learnings.md` をピンポイントで検索・読み込みます。
3. **タスク完了時（自己進化）**:
   新しいバグ修正や仕様の発見があった場合、エージェント自身が `Learnings.md` の末尾に知見を自律的に追記・更新します。


#### 2 層外部記憶の理論的ルーツと来歴
この 2 層メモリ設計は、AI エージェント研究における学術的成果と、実務における開発文化が融合して確立されたプラクティスです。

##### ① 学術研究におけるルーツ（外部メモリと自己反省）
モデルの重みを再学習させることなく、外部テキストによる記憶でエージェントを自己進化させるアプローチには、2 つの代表的な原典論文があります。

- **[Reflexion（Shinn et al., 2023 / NeurIPS 2023）](https://arxiv.org/abs/2303.11366)**:
  タスク失敗時にその原因と教訓を自然言語で自己反省（Self-reflection）し、**言語的メモリ（Verbal Memory）** に蓄積して次回の試行時に参照させることで、同一エラーの再発を劇的に防ぐ手法を実証しました。
- **[Voyager（Wang et al., 2023 / スタンフォード大・NVIDIA 等）](https://arxiv.org/abs/2305.16291)**:
  Minecraft 自律エージェントにおいて、獲得したスキルや実行手順をディスク上の **Skill Library（外部ライブラリ）** に保存し、必要に応じて動的に検索・再利用する自律学習モデルを確立しました。

##### ② 実務におけるデファクト化と命名の由来
2024〜2026年にかけてコーディングエージェント（Antigravity, Claude Code, Cursor 等）が実用化されると、開発者コミュニティで以下の実践が定着しました。

- **事後検証文化（Post-mortem）との接続**:
  シリコンバレーのエンジニアリング文化では、障害対応やプロジェクトの振り返りで得られた教訓を **「Key Learnings」** として文書化する慣習があります。これに倣い、エージェントに「セッションの教訓を記録せよ」と指示する際の標準ファイル名として **`Learnings.md`** が自然発生的に選ばれました。
- **Addy Osmani 氏による「Memory Primitive」の体系化**:
  Google の Addy Osmani 氏がエッセイ [『Loop Engineering』(2026-06-07)](https://addyosmani.com/blog/loop-engineering/) の中で、自律ループの必須要素として外部記憶（Memory）を位置づけ、*「The agent forgets, the repo doesn't（エージェントは忘れるが、リポジトリは忘れない）」* と定義したことで、この 2 層構造（常時ロード層 ＋ 自己進化層）がループエンジニアリングの基本設計として広く認知されました。

## Antigravity CLIにおけるループエンジニアリングの実践

Antigravity CLI（`agy`）において、上記の 3 つの核心要件をどのように設定・運用するか、当ブログ環境での構成例をもとに解説します。

### 5 つの基本要素の実装対応

| 構成要素 | Antigravity CLI での実装・ツール | 役割と設定ファイル |
| :--- | :--- | :--- |
| **1. Automations** | `/schedule`, `/plan`, CLI 非対話モード（`-p`） | 定期監視、ゴール駆動の自律完走 |
| **2. Worktrees** | `invoke_subagent`（`Workspace: "branch"`） | ブランチ・作業ツリーの完全分離 |
| **3. Skills** | `.agents/skills/*/SKILL.md` | 必要に応じた手順書（Runbook）のオンデマンド読込 |
| **4. Plugins** | GitHub MCP / Local Command ツール | 外部 API・Git・OS コマンドとの直接連携 |
| **5. Sub-agents** | `invoke_subagent` / `define_subagent` | 実装（Maker）とレビュー・テスト（Checker）の分担 |
| **+ Memory** | **`AGENTS.md`** ＋ **`Learnings.md`** | 基本方針（常時ロード）とナレッジベース（自己進化）の 2 層永続化 |


### 具体的な環境設定

#### 1. 権限設定（`settings.json`）
日常使用するコマンドを `~/.gemini/antigravity-cli/settings.json` の `permissions.allow` に登録します。

```jsonc
{
  "permissions": {
    "allow": [
      "command(hugo*)",
      "command(npm test*)",
      "command(git status)",
      "command(git diff)",
      "command(git log)",
      "command(git commit*)"
    ]
  }
}
```

#### 2. メモリ設定（`AGENTS.md` への 1 行指定）
公式規格である `AGENTS.md` の中に、自己進化ポリシーとして `Learnings.md` への参照指示を記述します。

```markdown
# 自律動作ポリシー
- **自律完遂**: 軽微な判断やエラー自己修復は質問を挟まず自律的に進める。破壊的変更のみ確認を行う。
- **自己進化**: 新たなトラブル解決やノウハウを発見した際は、自発的に `Learnings.md` へ追記してタスクを完了する。
```

> [!TIP]
> `AGENTS.md` に「知見は `Learnings.md` に追記・参照する」と 1 行指定しておくことで、エージェントが自発的にナレッジを蓄積・自己進化させるループが完成します。

### ループを回すための操作コマンド

#### ① ゴール駆動自律実行（`/plan`）
目的（ゴール）を渡し、計画立案からテスト・自己修復・コミットまでを自律完走させます。

```text
/plan 新規記事の構成を見直し、hugo --cleanDestinationDir で検証してコミットまで完了してください
```

#### ② 定期実行・監視ループ（`/schedule`）
Cron 形式で定期的にエージェントを起動し、監視やトリアージを自動化します。

```text
/schedule CronExpression="*/10 * * * *" Prompt="未コミットの変更やビルドエラーがないか確認し、あれば修復してください"
```

#### ③ セッション終了時の自己進化（`/learn` または自動記録）
タスク完了後、セッションで得られた新しい発見やルールを外部記憶に永続化させます。

```text
/learn 今回の修正で判明したテーマ CSS の仕様を Learnings.md に記録して
```

> [!NOTE]
> **/learn のデフォルトの書き込み先**
> 何も引数を指定せずに `/learn` を実行した場合、デフォルトではプロジェクト直下の公式ルールファイル（`AGENTS.md` や `GEMINI.md`）に直接追記されます。
> ただし、`AGENTS.md` 側に「*知見は `Learnings.md` に追記する*」という自己進化ルールを明記しておけば、引数なしの `/learn` でもエージェントが自律的に `Learnings.md` 側をターゲットとして選択・更新します。

## まとめ

AIコーディングエージェントの真価は、単なるコード生成の速さではなく、**「人間が介在しなくても、テストで検証しながら自分で直してゴールまでたどり着く自律ループ」** にあります。

プロンプトの言い回しに悩む時間を減らし、エージェントが快適に自走できる「ノンブロッキングな権限・高速な検証環境・2層の外部記憶」の整備に投資することこそが、これからの開発者に求められるループエンジニアリングの実践です。
